## 2. 設計項目

### D-01 データモデル（DDL）— 依頼(a)

**方針**: 既存の `type,key,value` 形式をそのまま 1 テーブルに写す。関数の戻り値（`load_settings` は辞書、`load_log` は `date`/`weight` の表）を変えずに済み、章 4〜8 の呼び出し側（303・375・448・534・624 行など）に手を入れなくてよい。型付きの 2 テーブルに分ける案は「テーブル 1 つ」の承認スコープを超えるため採らない。

置き場所: `migrations/0001_create_diet_data.sql`（当初案の `supabase/migrations/` から §9 で変更）。**実行は hiroki が Supabase の SQL Editor で行う**（私は接続しない）。

```sql
create table public.diet_data (
  type       text        not null check (type in ('setting', 'log')),
  key        text        not null,
  value      text        not null,
  updated_at timestamptz not null default now(),
  primary key (type, key),
  constraint diet_data_log_format check (
    type <> 'log' or (
      key ~ '^[0-9]{4}-[0-9]{2}-[0-9]{2}$'
      and case
            when value ~ '^[0-9]{2,3}(\.[0-9])?$'
            then value::numeric between 20 and 200
            else false
          end
    )
  )
);

-- 既定で全拒否にする（D-03）
alter table public.diet_data enable row level security;
revoke all on table public.diet_data from anon, authenticated;
grant select, insert, update, delete on table public.diet_data to service_role;
```

| 列 | 型 | 意味 |
| --- | --- | --- |
| `type` | text, NOT NULL, `'setting'` か `'log'` | 行の種別。CSV の `type` と同じ |
| `key` | text, NOT NULL | setting は項目名、log は日付（ISO） |
| `value` | text, NOT NULL | 値。CSV が全部文字列だったので同じにする（`60.0` が `60` に化けない） |
| `updated_at` | timestamptz, 既定 `now()` | 障害調査用。アプリは読まない |
| 主キー | `(type, key)` | 「同じ key は上書き」「1 日 1 行」を DB 側で保証する。CSV の「読んで消して足して書く」を 1 回の upsert に置き換える |

**この DDL は Postgres で実行して確認していない**（手元に Postgres が無い）。正規表現と CHECK の動きは、実装フェーズで hiroki が SQL Editor に流したあと I-12 で確かめる。

DB 側の CHECK は log 行だけ検査する（日付の形式、体重が 20〜200 で小数 1 桁まで）。暦として正しい日付かどうか、setting の値の検査は Python 側で行う（D-10）。

### D-02 Supabase 接続方式と鍵の選択 — 依頼(b)

**採用**: サーバ側（Streamlit）から `supabase-py` で REST（Data API）に接続し、**service_role 相当の秘密鍵**を使う。テーブルは RLS を有効にしてポリシーを 1 つも作らない（D-03）。

判断の根拠（比較）:

| 案 | 内容 | 判断 |
| --- | --- | --- |
| **A. 秘密鍵(service_role)＋RLS 有効・ポリシー無し** | 鍵は Streamlit サーバの secrets にだけある。ブラウザには届かない。Data API 経由の anon/authenticated は全拒否 | **採用**。パスワードゲートを迂回する経路が Supabase 側に残らない |
| B. anon 鍵＋RLS で全許可ポリシー | anon 鍵は「公開して良い鍵」の位置づけ。全許可にすると、URL と anon 鍵を知る人が誰でも読み書きできる | 不採用。ゲートは Streamlit 内にしか無く、DB は無防備になる |
| C. anon 鍵＋Supabase Auth でログイン | 本格認証 | スコープ外（承認範囲は単一パスワードのみ） |
| D. Postgres へ直接接続（接続文字列） | DB パスワードが鍵になる。Community Cloud からはプーラー経由の設定が要る | 予備案。設定項目と失敗要因が増えるため、A が動かない場合のみ検討 |

A の残るリスクと対策:
- 秘密鍵が漏れると DB を全操作される。→ 鍵は secrets にだけ置き、リポジトリ・ログ・エラーメッセージ・チャット・hive 内ファイルに出さない（D-12）。漏れた疑いがあれば Supabase 側でキーを再発行し、secrets を差し替える。
- 「service_role」は従来の呼び名。新しい管理画面では「secret key」等の名前になっている可能性がある。どちらでも「RLS を迂回できるサーバ専用の鍵」を使う、という方針は同じ。**実装フェーズの最初に、hiroki の画面を見ながら呼び名を確認する。**
- 無料プランではしばらくアクセスが無いとプロジェクトが一時停止する仕様がある（条件は hiroki が最新の案内で確認）。停止中はアプリが DB に届かない。D-09 のエラー表示で扱う。

### D-03 RLS と権限

- `enable row level security` かつポリシー無し → anon／authenticated は Data API から何も読めず、書けない。
- `revoke all ... from anon, authenticated` を重ねる（RLS の設定漏れがあっても権限で止める二重の備え）。
- `service_role` には明示的に権限を付与する（既定の付与に頼らない）。
- 確認方法: I-13（公開用キーで読み書きを試み、拒否されること）。

### D-04 パスワードゲートの実装方式 — 依頼(c)

置き場所（案）: `gate.py`（新規）。`app.py` は 1 か所から呼ぶだけにする。

処理の流れ:
1. `app.py:37-42` の `st.set_page_config(...)` の**直後**（`st.title` の前、44 行の手前）で `require_password()` を呼ぶ。`set_page_config` は最初の Streamlit 命令である必要があるので、その後ろで最も早い位置。
2. `APP_PASSWORD` が secrets に無い・空・空白のみなら、エラーを出して `st.stop()`（**失敗時は閉じる**。未設定のまま画面が開くことを許さない）。
3. `st.session_state["authed"]` が `True` なら通す。
4. 通っていなければ `st.form`（パスワード入力＋送信）だけを表示する。送信されたら `hmac.compare_digest`（UTF-8 のバイト列同士）で比較する。一致したら `authed = True` にして `st.rerun()`。
5. 一致しなければ「パスワードが違います」を出し、`st.stop()`。
6. ゲートを通るまでは、`st.stop()` により 44 行以降が実行されない。DB 読み出し（303 行以降）も、サイドバーのリセットボタン（282 行）も動かない。

session_state はサーバ側にあり、ブラウザから書き換えられない。ページを再読み込みすると再入力になる（Cookie 保存は行わない。外部部品が増えるため）。

### D-05 総当たり対策（軽量）

- プロセス全体で共有するカウンタを `st.cache_resource` に置く（新しいタブで回避されないため）。
- 連続 5 回失敗したら 60 秒ロック。ロック中は**正しいパスワードでも拒否**する。成功したらカウンタを 0 に戻す。
- 残るリスク: アプリの再起動でカウンタは消える。ロックは攻撃者にも本人にも効く（本人が 60 秒待つだけ）。実質の防御は**長くランダムなパスワード**。この点は hiroki に伝える。
- 追加で Community Cloud 側の「閲覧者を限定する共有設定」を重ねる案がある（プランと条件は要確認。この設計では前提にしない）。

### D-08 読み出し回数と 1000 行の上限

- 1 回の rerun で最大 5 回の読み出しがある。CSV では無視できたが、DB では往復が 5 回になる。→ `fetch_all()` の結果を `st.cache_data(ttl=60)` で共有し、書き込み成功のたびに `clear()` する。書き込み直後の rerun は必ず最新値を読む。
- 自分だけが使うため、キャッシュがセッション間で共有されても漏えいにはならない（読み出しはゲートの後だけ）。ただし Supabase の管理画面で直接直した値は最大 60 秒遅れて見える。
- PostgREST の 1 回の取得は既定で最大 1,000 行に切られる。日々の記録が 1 日 1 行なので、約 2 年 9 か月で上限に達し、古い（または新しい）記録が**黙って欠ける**。→ `fetch_all()` は 1,000 件ずつ範囲指定で最後まで取得する（U-07）。

### D-09 失敗時の動き

仕様に失敗時の挙動は書かれていなかったため、次を提案し、Q-04 で承認された:
- 読み出し失敗: 「データベースに接続できませんでした。時間をおいて再度お試しください」を表示して `st.stop()`。空のプランを出すと「データが消えた」ように見えるため、描画自体を止める。
- 書き込み失敗: 同じ文言を表示して `st.stop()`。成功メッセージを出さない。
- エラー文には URL・鍵・例外の生の文字列を含めない（`DataStoreError` のメッセージは固定文）。詳細はサーバのログにだけ残し、そこにも鍵は出さない。

### D-10 入力の検査（データ層）

UI の範囲と同じ検査を `db.py` でも行う（UI を通らない呼び出しや将来の変更に備える）。
- 体重: 有限の数値で 20.0〜200.0。**小数 1 桁に丸めて**保存する（`66.30000000000001` → `"66.3"`、`66` → `"66.0"`。DDL の書式制約に合わせる）。
- 日付: `YYYY-MM-DD` の文字列で、暦として正しいこと（`2026-02-30` は拒否）。
- setting の key は 4 つの許可リスト（D-01 の表）。それ以外は拒否。値は `start_weight`・`goal` が 20〜200、`deadline`・`start_date` が ISO 日付。
- 検査に落ちたら `InvalidInputError`（DB へは送らない）。
- SQL はパラメータ化された REST 呼び出しで、文字列連結の SQL は書かない。

## 9. T-005: `supabase/` ディレクトリ名の衝突（実装後に判明）

- 事象: hiroki のローカル起動で、ログインのあとに「データベースに接続できませんでした」と表示された。プロジェクト直下で `import supabase` が pip 版ではなくローカルの `supabase/`（DDL を置いたディレクトリ）を指し、`from supabase import create_client` が `ImportError: cannot import name 'create_client' from 'supabase' (unknown location)` になっていた。
- 原因の切り分け（実測）:
  - `supabase` が**入っていない** Python（手元の `/opt/anaconda3`、`/Library/Frameworks/…`、`/usr/local/bin` の 3 つで確認）では、直下の `supabase/` が名前空間パッケージとして解決され、上記の ImportError になる。
  - `supabase` が**入っている** Python（新しい venv）では、直下から実行しても、直下をパスの先頭に足しても、pip 版が優先される（`supabase.__file__` は site-packages）。
  - つまり、直接の原因は「起動に使っている Python に `supabase` が入っていない」ことで、ローカルの `supabase/` は、それを分かりにくい ImportError に見せていた。両方を直す。
- 設計・確認の見落とし: D-06 の配置案（`supabase/migrations/`）は、pip の `supabase` パッケージと同名になることを検討していなかった。手元のテストが通っていたのは、`supabase` を入れた venv で実行していたことと、`make_client` の import を遅延させていたことによる。
- 対応: (1) `supabase/` を `migrations/` にリネームし、参照（README、実行手順書、設計.md）を更新。 (2) 手順書に「手順 0: 起動に使う Python に依存を入れる」を追加。 (3) `make_client` は import 失敗（`ImportError`）を別ログで出す（画面の文言は従来どおり固定文。鍵は出さない）。 (4) 回帰テスト 2 本を追加（`tests/test_environment.py`）。データモデル・ロジック・セキュリティ設計は変更していない。
